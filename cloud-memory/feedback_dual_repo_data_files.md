**data/shows.json, data/reviews.json, and other core data files are authoritative in the private `broadway-scorecard-data` repo — NOT the public `Broadwayscore` repo.** Edits to the public copy get silently overwritten at deploy time.

**Why:** The Vercel deploy workflow has a "Checkout core data" step (`.github/actions/checkout-core-data/action.yml`) that clones `broadway-scorecard-data` into `/tmp/core-data-checkout` and copies ALL `*.json` files on top of `data/`. So whatever is in the public repo's `data/shows.json` is replaced with the private repo's version before the Next.js build runs. Found in WE pre-Reddit-launch audit (2026-04-11): I pushed R&J synopsis + Royal Court OWE recategorization to `data/shows.json` in the public repo, the deploy succeeded, but the changes were silently reverted because the private repo still had the stale content.

**How to apply:**
- `data/reviews.json` is a symlink to `~/broadway-scorecard-data/reviews.json` (already gitignored + untracked)
- `data/shows.json` is now a symlink to `~/broadway-scorecard-data/shows.json` (converted 2026-04-11, see commit on both repos)
- When editing either file locally via Edit/Write/node scripts, **the change writes through the symlink to the private repo** — you still need to `git add/commit/push` in `/Users/tompryor/broadway-scorecard-data/` to make it permanent
- All the other core data files (awards, critic-registry, outlet-registry, etc.) live in the private repo only and are pulled into `data/` by `setup-local-data.sh`. Edits to those files would also need to be pushed to private.
- **Never commit `data/shows.json` or `data/reviews.json` to the public `Broadwayscore` repo** — they are gitignored (lines 119, 120 of `.gitignore`). If you see them staged, something is wrong.

**The multi-repo regression trap:** Even pushing to the private repo isn't enough protection. CI workflows that run on the public repo (`gather-reviews`, `rebuild-reviews`, `enrich-*`, `auto-maintain`) modify `data/shows.json` in the public workspace and then call `push-core-data` action to sync back to private. If ONE of those workflows runs with stale input (e.g., a merge conflict resolved "take theirs"), it silently reverts your fix on BOTH repos.

**Worked example (2026-04-11):** I recategorized 10 Royal Court shows to OWE in session commit `d77c6d4be4`, pushed to both public and private. A few hours later, public commit `0ab0afb016 "Resolve merge conflict on validation-baseline.json (take theirs)"` ran on the public repo — its merge conflict resolution "took theirs" on `data/shows.json` as a side effect, reverting all 10 Royal Court categories. That commit then propagated to the private repo via `push-core-data`. I had to re-apply the fix directly in the private repo (commit `f7e0064`) and verify the public repo never sees `data/shows.json` again.

**Future session checklist before editing core data:**
1. `git -C /Users/tompryor/broadway-scorecard-data log -5 --oneline` — check the private repo isn't mid-rebuild
2. Read `data/shows.json` via the symlink to get the freshest state
3. Edit + `git -C /Users/tompryor/broadway-scorecard-data commit + push`
4. After session, verify fix survived by reading live broadwayscorecard.com data URL with a cache-bust query param
5. If a CI workflow ran during the session, re-check — it may have clobbered your fix. Re-apply if so.

**Worktree addendum (2026-07-15):** A fresh worktree does NOT inherit the main checkout's `data/shows.json` symlink — it's gitignored/untracked, so `git worktree add` never creates it. `data/shows.json` will be plain-missing in a new worktree until you manually `ln -s /Users/tompryor/broadway-scorecard-data/shows.json data/shows.json` (same for reviews.json, critic-consensus.json, review-texts/). **Also:** `atomicWriteShowsJson()` (scripts/lib/atomic-shows-write.js) writes via `fs.renameSync(tmpPath, targetPath)` — POSIX rename REPLACES a symlink at `targetPath` with a real file rather than writing through it. If `data/shows.json` is a symlink when an atomic-write script runs, the write silently lands in an orphaned real file in the worktree's `data/`, NOT in the private repo — `git diff` in the private repo will show nothing changed. Safer: run write scripts with `SHOWS_FILE`/cwd pointed directly at `/Users/tompryor/broadway-scorecard-data/` (or a one-off `node -e` requiring the pure logic against that absolute path) instead of through a worktree's symlinked `data/`.

**BSC_DATA_REPO env override (2026-07-20):** `scripts/check-data-health.js` locates the private clone via `process.env.BSC_DATA_REPO || ~/broadway-scorecard-data`. ~20 other scripts still hardcode the path; when touching one, prefer adopting this env var. Staleness there = clone sync time (FETCH_HEAD mtime) for files symlinked/identical to the clone — file mtime alone lies for symlinks (false "2d stale" fixed this date).

**Worktree hard-blocks git ops in other repos, incl. data/review-texts (2026-08-15, task #1533).** `data/review-texts` is its own gitignored git clone (real directory, not a symlink — see [[feedback_review_texts_not_symlink.md]]), same dual-repo pattern as shows.json/reviews.json. From an EnterWorktree session, the harness itself (not git) hard-blocks any git command targeting a path outside the current worktree — `cd data/review-texts && git ...`, `git -C data/review-texts ...`, even from the main repo's own subdirectory, all get refused with "a worktree-isolated session's git operations must target its own worktree." Node/python scripts pointed at the absolute private-repo path work fine (no block on non-git file I/O) — only `git` itself is gated. To commit/push a private-repo data file (review-texts, or broadway-scorecard-data) after finishing a worktree-based script edit: `ExitWorktree({action:"keep"})` first, do the private-repo git ops from the restored main-repo cwd, then merge the worktree branch into main separately. Don't try to work around the block with tricks — it's enforced at the tool layer regardless of shell syntax.

**CI-side gotcha: `git show HEAD:data/X.json` / `git diff --quiet data/X.json` silently lie in workflows (2026-08-13, card #1439 ship-check + card #1441 cousin find).** In `.github/workflows/*.yml`, these core-data files are gitignored and NEVER committed to this repo's git history — `git ls-files data/shows.json` returns nothing. `git show HEAD:data/shows.json` therefore always fails (no such path at HEAD); `git diff --quiet data/awards.json` on an untracked path reports "no differences" regardless of real content changes (untracked files aren't part of `git diff` at all). Both read as false negatives, not errors — a workflow using either as its before/after or changed-file signal silently no-ops forever. The correct pre-run baseline in a workflow is `/tmp/core-data-snapshot/$f`, written by `checkout-core-data` (`.github/actions/checkout-core-data/action.yml`) specifically for this — see `scripts/lib/core-data-sync-decision.js` for the established diff convention, and `scripts/lib/shows-since-checkout-diff.js` for a worked example. Found live in `update-tony-awards.yml` (card #1441): it uses both broken forms AND has no `push-core-data` step at all, so it likely never actually persists a scrape. **Before writing a new before/after or changed-file check against any `data/*.json` in a workflow, `git ls-files data/<file>` first — if empty, use the snapshot, not git.**
