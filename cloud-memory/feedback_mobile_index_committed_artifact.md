`public/data/mobile-shows.json` (the mobile INDEX consumed by the iOS app) is a **git-tracked, committed** artifact — and on `SKIP_HEAVY_PREBUILD=true` (code-only) Vercel deploys the committed copy is served **verbatim** (prebuild.sh regenerates the per-show DETAIL files but NOT the index under skip-heavy). So a stale committed index is shown to real users, not just a CI fixture.

The bug: the rebuild pipeline (`rebuild-fast.yml`, `rebuild-reviews.yml`) regenerated the per-show detail files (`generate-mobile-show-details.js` → `public/data/shows/*.json`) and committed them, but **never** regenerated/committed the index (`generate-mobile-data.js`). The index was only ever refreshed by sporadic `opening-night-broadcast.yml` runs (which actually generate-then-discard — they never `git add` it) and by `prebuild.sh` full-builds / hand commits. So whenever a rebuild dropped a closed show's last scored review, the committed index kept the now-closed-no-score show. Once >5 accumulated, `validate-mobile-shows.js` (tolerance `MAX_CLOSED_WITHOUT_REVIEWS=5`) reddened the test.yml Data Validation gate. Regenerating by hand was proven-temporary (commits a783105dac drop-6, 5428b2b169 drop-51).

**Fix (2026-06-22):** regenerate the index in BOTH rebuild workflows in lockstep with the detail JSONs, and `git add public/data/mobile-shows.json` in the existing `has_changes==true` commit step. The index is a pure function of reviews.json/shows.json, which change on essentially every real rebuild, so the index now stays fresh and the validator stays a trustworthy blocking integrity gate.

**Why:** A committed derived artifact that is served to users but only regenerated by a sporadic, unrelated workflow WILL drift. The detail files were kept fresh by the rebuild pipeline; the index was the forgotten twin. Symmetry (regenerate both wherever you regenerate either) is the durable invariant.

**How to apply:**
- The index output is **single-line minified JSON with a `_ts` timestamp** (`generate-mobile-data.js` line ~235). So it is NOT byte-deterministic and you CANNOT cheaply `git diff -I'_ts'` it (the whole file is one line). Therefore: stage it ONLY inside the `has_changes==true` block (gated on reviews.json + public/data/shows/ diffs) — never add it to the change-gate, or the changing `_ts` forces a commit+deploy on every no-op rebuild tick and breaks rebuild-fast's byte-identical-no-op contract.
- Residual edge case: a show whose STATUS flips closed in shows.json with NO concurrent reviews.json change can drop from the index without `has_changes` firing (the detail generator uses the same `visibleShows` filter, so it leaves the excluded show's detail file untouched — no `public/data/shows/` diff either). This is rare (bulk historical reclassification, e.g. the 51-show 2002–2003 event) and is exactly what the validator's tolerance-5 + the validator-as-backstop catches; frequent rebuilds (reviews.json changes constantly) heal it within hours. Don't over-engineer a content-diff into the change-gate.
- Concurrency: `rebuild-fast` (per-run concurrency group) and `rebuild-reviews` can run concurrently and both commit this monolithic file. `push-with-retry.sh` Attempt-1 is `rebase -X theirs` = keep OUR fresh index, so the common path is safe; the per-file "accept remote" fallback only triggers on a messy conflict and self-heals on the next rebuild. Acceptable for a tolerance-5 derived artifact.
- If you ever make the index fully deterministic (drop `_ts` or move it out of the served blob), you can then add it to the change-gate plainly and tighten the validator to assert index↔reviews.json consistency. Until then, lockstep-regenerate + has_changes-staging is the pattern.
- Follow-up worth doing: extract a shared `scripts/generate-mobile-artifacts.sh` (details + index) called from all ~7 sites so the two can never drift apart again. Deferred 2026-06-22 to keep the fix minimal. See [[feedback_test_yml_data_gates_flap_and_shortcircuit.md]] for the broader test.yml de-flaking pattern (drift gates → check-*-drift.yml; integrity gates stay blocking).
