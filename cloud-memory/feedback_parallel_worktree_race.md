## Main repo working tree can be mid-conflict from another session (2026-07-14)
`git checkout main && git merge <worktree-branch>` in the MAIN repo's working directory can hit `error: you need to resolve your current index first` — another parallel session left main's working tree with unrelated staged/conflicted files (e.g. mid-resolution of a `.github/workflows/test.yml` conflict from its own merge). This is not your conflict to resolve — you don't have context on the right resolution, and `git merge --abort` or force-checkout could destroy that session's in-progress work.

**Fix:** don't touch the main repo's dirty state. From the worktree, `git push origin <branch>`, then `gh pr create --base main --head <branch>` and `gh pr merge <PR> --merge` — this is a server-side GitHub merge that never touches the local main repo's working directory at all. Confirmed safe: the other session's conflict resolution is untouched, your branch lands on origin/main via the API.

## High-churn main: manual fetch/rebase/push loop can lose every race (2026-07-19)
During a burst of concurrent worktree sessions all merging to main (observed: 6 consecutive `git push origin <branch>:main` rejections in ~5 minutes, each against a DIFFERENT new tip), a manual `git fetch origin main && git rebase origin/main && git push` loop kept losing — by the time local verification (tests) finished, another session had already pushed again. **Better fix for next time:** reach for `gh pr create --base main --head <branch>` + `gh pr merge <PR> --merge --auto` (or plain `--merge` once mergeable) instead of a manual retry loop — same fix already documented above for the "dirty main working tree" case, but it also solves THIS race: GitHub resolves the fast-forward server-side, so you're not manually racing every other session's push. Should have reached for this immediately instead of 6 manual cycles.

## Checking out a branch in the shared main checkout can hijack another session's merge target (2026-07-26)

**Fix:** never run `git checkout <branch>` (or anything that changes HEAD) in the shared main repo directory, even briefly, even to isolate your own commit. Recovery when it does happen: don't touch the other session's conflict (same rule as the entry above) — it self-resolved when they re-checked-out main independently, confirming their branch/commits were never at risk, only the shared checkout's transient state.

## Recovery recipe when a worktree branch needs to reach origin/main and a full rebase hits someone else's conflict (2026-07-31)
Task #674: after committing 2 commits on a worktree branch, `git rebase origin/main` (run from inside the shared main checkout, violating the entry above) replayed the ENTIRE branch history and hit an unrelated scoring-logic conflict in `scripts/llm-scoring/index.ts` between two other concurrent sessions — not mine to resolve, and the working tree filled with ~30 live-CI-modified data files mid-rebase. `git rebase --abort` cleared it, but the branch pointer had already been reset by an earlier `git checkout main` in the same shared dir, leaving my follow-up commit dangling (recoverable via reflog, but easy to lose).

**Fix — do the whole thing from inside your own worktree, never `cd` to the shared main dir at all:**
1. `git rebase --onto origin/main <commit-just-before-your-first-commit> HEAD` — replays ONLY your own commits onto the current origin/main tip, skipping every intervening merge/conflict entirely (this is the key difference from plain `git rebase origin/main`, which walks the branch's full ancestry from whatever stale base it forked from).
2. `git branch -f <your-branch> HEAD && git checkout <your-branch>` to make the rebase result the branch tip (the rebase leaves you in detached HEAD).
3. Retry-push loop, entirely from the worktree: `git fetch origin; git merge-base --is-ancestor origin/main HEAD || git rebase origin/main; git push origin HEAD:main` — repeat on rejection (a busy repo can reject 2-3x in a row). Because step 1 already isolated just your file's diff, each retry's rebase is a no-conflict fast-replay, not a fresh merge.
4. If a conflict DOES appear during a retry rebase in an unrelated file: that's someone else's live work colliding with your file, not yours to resolve — `git rebase --abort` and re-do step 1 with `--onto` again against the newer origin/main, don't try to resolve their side.

## SHA-reachability is not proof your files landed — verify actual content (2026-07-31)
Task #677: after `push-with-retry.sh` reported "Push succeeded" and `gh api compare <mySHA>...main` returned `identical`, the entire deliverable (6 new files, wiring in 2 modified files) was later found completely absent from origin/main. Root cause: `git reflog` showed a `reset: moving to origin/main` fired in the shared main checkout between two of THIS session's own merge/push cycles — it silently discarded the rebased commits containing the work before they were ever pushed, then a later merge landed cleanly from the now-work-free base. The pushed SHA I checked was real and reachable — it just didn't contain what I thought it did, because local HEAD had already been reset out from under it before I captured that SHA for verification.

**Fix:** a `gh api compare A...B` returning `identical`/`ahead` only proves commit A is on origin — it does NOT prove A contains your work, if A itself could have been produced by a broken rebase/reset. After any push under high concurrent churn (multiple sessions merging to the same shared main checkout), verify actual FILE EXISTENCE/CONTENT on origin directly: `git cat-file -e origin/main:<path>` for every new file, `git show origin/main:<path> | grep -c <marker>` for wiring changes to modified files. Recovery when it's missing: `git reflog` usually still has the pre-reset commit (not yet gc'd) — `git checkout <reflog-sha> -- <paths>` restores the exact content to recommit on the current tip.

## Subagents inherit worktree isolation; committing to a shared private data checkout needs value-diffing, not line-diffing (2026-09-14)
BRO-3250: a healer script's `--fix` accidentally ran (twice) against the real, shared `~/Broadwayscore/data/review-texts` checkout (a separate private-repo clone, not the code worktree). Two lessons: (1) a subagent dispatched from inside a worktree-isolated session inherits that same isolation and cannot reach a directory outside the worktree either — the only way back to the shared main checkout was `ExitWorktree(action: "keep")` from the top-level session itself (worktrees with no unmerged commits vs main are safe to exit; nothing was lost). (2) `git diff --stat` on the shared checkout showed far more changed files than the script should have touched — other live sessions/CI bots write to the SAME checkout concurrently, and a plain `git diff -U0 | grep '"fieldName"'` line-scan false-positives on trailing-comma-only churn from a NEIGHBORING field. Fix: parse `git show HEAD:<file>` vs the working-tree file as JSON and diff by KEY VALUE, not by diff line, to separate "my intended field changes" from "someone else's concurrent edit that happened to land in the same file between my read and write." Files with only my allowed keys changed → stage+commit; anything else → leave untouched (don't even attempt to un-mix a shared file — could be right in the middle of that other process's own next write). During the retry-push loop this also surfaced that the CI pipeline I'd just wired in had ALREADY run for real and applied the same fix upstream — my rebase found the diff already present and auto-dropped my now-empty commit, which is correct behavior, not data loss; verify via the live site/derived data, not just "did my commit land."

**How to apply:** before running any `--fix`/`--apply` script locally against a shared, non-worktree data checkout (review-texts, or any private data repo), assume other sessions/CI are writing to the same files concurrently. After the run, JSON-value-diff (not `git diff` text-scan) to isolate your own field changes before staging. If you need the shared main checkout from inside a worktree session, `ExitWorktree` yourself (ask the user first per the tool's own restriction) — don't waste a subagent dispatch on it.

## `push-with-retry.sh`'s `reset --hard origin/main` step assumes a clean working tree — check first (2026-09-16)
BRO-2392: went to merge a worktree branch (a small, isolated fix) into the shared main checkout per the documented `git checkout main && git pull && git merge <branch> && git push` pattern. `git status` in the shared checkout showed 13 dirty entries — modified `data/audit/*.jsonl`/log files and several untracked `HANDOFF-*.md` scratch files, all clearly other concurrent sessions' in-flight state, none touched by my branch. `git pull --ff-only` then failed with "diverging branches" (local main had moved ahead of origin/main too, from other sessions' local commits). The documented retry loop's next step would be `git fetch && git reset --hard origin/main && git merge <branch> --no-edit && git push` — but `reset --hard` unconditionally discards the working tree's uncommitted changes, which here would have destroyed other live sessions' uncommitted audit logs and handoff notes.

**Fix:** before running `reset --hard origin/main` (or any step of the documented merge-retry loop) in the shared main checkout, `git status --short` first. If it shows uncommitted changes to files your branch doesn't touch, that's not idle/disposable state — it's a live session's in-flight work, same class as the MERGE_HEAD-ownership entry above. Don't reset it away. Instead: leave your branch pushed to origin (`git push origin <branch>`) and stop there — this repo has dedicated fleet tooling for exactly this state (`scripts/reconcile-landed-but-open.js`, `scripts/audit-stranded-reviewed-branches.js`, and an owner-run batch-merge pass for "unmerged branches with passing verdicts"), so a pushed branch with a recorded `ship-check` pass verdict is a normal, expected, safely-picked-up-later state — not an incomplete session. Report it as such rather than forcing a risky manual reconciliation.

## Committing to a shared PRIVATE DATA repo clone (not the code checkout) when another session has staged files there too — use pathspec commit, not `-a`/`-A` (2026-09-25)
BRO-4156: mid-fix in `~/broadway-review-texts` (the review-texts private data clone, shared across sessions same as the main checkout), `git status` showed staged/unstaged changes on files I never touched (a DIFFERENT ticket's Andrzej Lukowski/Alice Saville domain-collision fixes) sitting in the index alongside my own edits. `git commit -m "<mine>" -- <my 3 files>` errored "pathspec did not match any file(s) known to git" for one path — turned out the OTHER session's own commit had landed in the ~1s gap between my `git status` check and my `git commit` call, and its commit (a plain `git commit -am`-style call, no pathspec restriction) had swept up my already-staged `git rm` of a file I'd deleted, along with its own 3 files, into ONE commit under its message. My command's pathspec then failed because that path no longer had anything to commit relative to the new HEAD — but nothing of mine was lost (their commit already contained my deletion) and no partial/wrong commit was created (git commit aborts entirely on a pathspec miss).

**Fix:** in a shared clone (private data repo OR the main checkout), commit with an explicit trailing pathspec of ONLY the files you intend — `git commit -m "..." -- path/one path/two` — never `-a`/`-A`/bare `git commit` when `git status` shows entries you didn't create; that pathspec form commits exactly those paths regardless of what else is staged, and leaves the other session's staged files exactly as they were for their own eventual commit. If the commit then errors with "pathspec did not match any file(s)" on a path you know you touched, don't assume you made a mistake — re-run `git status`/`git log -1` first: it usually means a concurrent session's commit just landed and already carries your change (verify via `git show --stat HEAD` before redoing anything).

## A textually clean merge can still land a semantically contradictory fix (2026-09-16)
BRO-3586: fixed a red unit test (`wrong-production-setters-honor-manual-clear.test.mjs`) by adding a real `shouldSkipWrongProductionAudit` guard to `audit-corpus-contamination.js` and registering it in `KNOWN_SETTERS`. **Fix:** after merging a worktree branch whose fix targets a previously-red shared test/gate, grep the merged file for your own fix's target identifier (e.g. the script/flag name) and confirm it appears with ONE coherent resolution, not two — a clean merge and a passing test are not proof that two independent fixes for the same symptom agree with each other.
