Two compound-command traps that each bit multiple times in one session (2026-07-12/13):

**1. zsh does not word-split unquoted variables.** `FILES="a b c"; git restore --staged $FILES` passes ONE pathspec `"a b c"` (fails); `MK="node script.js"; $MK args` tries to exec a binary literally named `node script.js`. Bash-isms silently break. **Fix:** iterate (`for f in a b c; do ...done`), or write the whole harness as a node script file and invoke it — no interpolation surface at all.

**2. `git stash push` → work → `git stash pop` chains are unsafe in this repo.** `stash push` saves NOTHING when the tree is clean ("No local changes to save") — the later `pop` then pops a DIFFERENT, pre-existing stash from a parallel session onto main, and a follow-up `stash drop` deletes yet another one. This repo always has parallel sessions' stashes present. **Fix:** never pop unconditionally. Either check the push actually saved (`git stash push ... | grep -q "Saved"` and only then pop), or skip the stash entirely when `git status --porcelain` is empty. Dropped stashes are recoverable by the hash printed at drop time (`git stash apply <hash>`).

**Also (same family, from feedback_prepush_gate_stash_push_parser):** the word `push` in `git stash push` confuses the pre-push hook's target parser — keep `git push` in its own command.

**4. A Bash call that mixes an `&&` chain with SEPARATE newline commands half-executes on failure (2026-07-13).** During a mid-rebase conflict resolution: line 1 was `cd data/review-texts && python3 <<EOF …resolve markers… EOF`; lines 2+ were `git add … && git rebase --continue && git push`. The `cd` failed (cwd was already there, relative path invalid), so the python resolution never ran — but the newline-separated git lines still executed and PUSHED a JSON file with `<<<<<<<` conflict markers to origin. **Fix:** during conflict resolution, one Bash call = one step; after any resolution, verify the file parses (`node -e 'require(...)'` / `python3 -c 'json.load…'`) in the same call as the `git add`, and re-read the pushed file from `origin/<branch>` before claiming it's clean.

**5. `git pull --rebase` after a rejected push of a worktree merge commit flattens the merge (2026-07-13).** Sequence that bit: merge worktree branch → main, push rejected (remote advanced), `git pull --rebase` — rebase REWRITES the merge as flat cherry-picked commits with new SHAs. Main now has a *copy* of the worktree commits with no shared ancestry, so the NEXT `git merge <worktree-branch>` hits content + add/add conflicts on every file the branch touched. **Fix:** when integrating a worktree merge into a moved remote, use `git pull --no-rebase` (merge), or rebase the WORKTREE BRANCH onto origin/main and re-merge. If already bitten: resolve with `git checkout --theirs <files>` (worktree branch versions are the superset) and verify `git diff --cached <branch> -- <files>` is empty.

**6. A `cd` on its own line at the top of a multi-line Bash call persists for EVERY later line in that same call, including cleanup lines added for an unrelated purpose (2026-07-26).** In a worktree session, one Bash call opened with `cd /path/to/MAIN-REPO` followed by several `ln -sfn` lines (intentional, to symlink private data into the main repo for a one-off audit script run) and ended with a `rm -f data/shows.json data/reviews.json data/review-texts` cleanup line — the cleanup was meant for the worktree but ran in the main repo instead, deleting its real `data/shows.json`/`data/reviews.json` symlinks and leaving a stray self-referential symlink inside the real `data/review-texts/` directory (the `ln -sfn TARGET data/review-texts` line silently nested a symlink inside the existing directory rather than replacing it, since the target was already a real dir, not a symlink). No repo damage (gitignored, easily recreated) but a live worktree-enforce hook near-miss. **Fix:** never let a `cd` in one Bash call outlive its original purpose — either scope one `cd` to one command (`cd X && cmd`), or repeat the FULL absolute path on every line and skip `cd` in multi-line blocks entirely, especially when a worktree and its main repo are both in play.
