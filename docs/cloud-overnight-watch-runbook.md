# Overnight watches from a cloud session

Moved out of `.claude/CLOUD.md` (BRO-7315) so it is read when a watch is planned, not by every session. The text is unchanged.

The owner lives in Berlin; US opening-night reviews drop 01:00-03:00 UTC. Anything needing their tap then fails (`list_sessions`/`create_session` prompt too, even in Auto mode), so a watch that re-arms itself with `send_later` dies after one pass.

0. **One session owns press night (BRO-6585).** The coordinator session (BRO-5955 lineage) owns every aggregator-listed review live and scored, and the lane trial, and starts fix workers. Any other session asked about that night reads the coordinator card first (`node scripts/coordinator-check.js --card BRO-N`), reports to the coordinator, and lands nothing for that show without its go. A hand-added review muddies the trial grade: only the coordinator adds one, recorded as manual.
1. **Reviews don't depend on a Claude watch.** `opening-night-orchestrator.yml` fires ~01:00-01:20 UTC nightly and dispatches the poller every 15 min for ~4.5 h; `aggregator-url-watcher.yml` runs every 5 min. Confirm they're armed (`node scripts/check-opening-night-readiness.js --show=ID`, recent orchestrator runs). For a show the opening-night lane publishes (`LANE_ONLY_MARKETS` covers it, currently Broadway), that same command also reports the embargo time, whether the lane is armed, whether the lane night run and its watchdog are active for the night, and which pipeline commits landed in the last 48h; the lane, not the orchestrator, is the primary publisher there (BRO-7548).
2. **If a Claude supervisor watch is wanted, use what needs no owner tap first (BRO-7880).** In order: (a) a GitHub Actions cron or workflow that already runs that night; (b) a background Bash or Monitor in a session that stays awake through the window; (c) a held card for each check (`node scripts/linear-brain.js create "<title>" --dispatch --priority 1 --not-before <ISO time> --notes "<what to check, with a VERIFY: line>"`): a board worker takes it after that time. Never ask the owner to approve a schedule or to reply "yes" to one.
   Last resort, only when the owner asked for the watch themselves and none of (a)-(c) fits: schedule every pass while the owner is awake, in one go, and tell them before the prompts appear. `create_trigger` with `initiation: "human_request"` and `persistent_session_id`. Minimum interval is 1 hour, so a 20-min cadence is three routines: `1 0-5 <day> <month> *`, `21 0-5 …`, `41 0-5 …`, `<day>` = the UTC date reviews land (the day after a New York opening). Avoid minute 0; check `next_run_at`. Add a `run_once_at` morning routine that deletes the three. Every pass prompt says: never call `send_later`/`create_trigger`, never relabel `initiation`. Point frequent passes at a lean `create_session` session.
3. **The first reply on press night answers every owner question in a status table (BRO-7890 item 11).** When the owner sends several questions (is the score up, was the email sent, why is review X missing, is the lane running), the first reply is one table, one row per question, columns: question, answer, evidence (a link or the check you ran), still open. No row is left for a later message, and "checking" is not an answer: run the check first. Plain words, no ids or paths in the table.
4. Never plan a watch that re-arms itself, and never rely on ScheduleWakeup firing. `fire_trigger` doesn't rehearse this: it starts a new session without the repo.


## A review is missing on a lane night (BRO-7741)

Do not roll back the lane. Put the URL in the lane's inbox; the running lane reads it every pass (about 2 minutes), fetches, scores and publishes it, and records it as manual (`openingNightLane.source: 'manual'`, no guard bypass).

1. `node scripts/opening-night-lane-inbox.js add --show=SHOW_ID --url=URL [--critic="Name"] [--outlet=ID]`, or dispatch `ingest-urls.yml` by hand with the show and URL: for a leased show it now routes the URL into the inbox and says so in a `::notice::` line instead of reverting it.
2. `node scripts/opening-night-lane-inbox.js list --show=SHOW_ID` shows what the lane did: published, failed (with why), rejected (with why, e.g. dated outside the night), already-in.
3. A page whose date is wrong is rejected as outside the night window. Re-add it with `--force`; the running lane picks the re-add up on its next pass.
4. Whatever the lane did not finish goes to `ingest-urls.yml` after the lane releases its lease (the "Drain the lane inbox" step). If that step is skipped or the show is still held, the hourly sweep in `opening-night-checklist.yml` (`opening-night-lane-inbox.js sweep`) sends anything left open for 6 hours once no lane holds the show, and re-sends a drained or already-in URL still missing from reviews.json after 2 hours (up to 3 times). Entries expire 72 hours after they were added.
5. `add` refuses (exit 2) when no lane holds the show, because nothing would read the inbox: dispatch `ingest-urls.yml` instead, or pass `--queue-anyway` to queue a URL before tonight's lane starts.

Kill switch: repo variable `OPENING_NIGHT_LANE_INBOX_DISABLED=true` (the lane ignores the inbox; ingest-urls still writes to it, and the drain sends those URLs to ingest-urls after the night).
