# .claude/CLOUD.md — read first if you're a cloud Claude Code session

Cloud Claude Code apps (claude.ai/code, iOS, Mac desktop) run in stateless sandboxes that DON'T mount the owner's real `~/.claude/` config dir (the Mac's hooks, slash commands and memory; counts change weekly).

**The owner's global instructions usually ARE loaded** (BRO-4237): `.claude/hooks/session-start.sh` fetches `CLAUDE.md` + `anti-slop-rules.md` from the private `thomaspryor/claude-config` repo at every cloud start and installs them as `~/.claude/<file>`, so you and your subagents have them. Their "## Cloud sessions" section overrides Mac-only rules. If the fetch failed, session-start printed a short owner fallback plus the reason instead.

This file + a small set of project-scoped substitutes (`.claude/hooks/`, `cloud-memory/`) bring you closer to local CLI behavior.

## Before your first tool call

1. **Verify secrets:** `node scripts/check-cloud-secrets.js`. Env vars are set ONLY in the web UI (there is no CLI/API/repo-file path — verified against the official docs): claude.ai/code → **cloud icon showing the current environment's name** → hover environment row → **gear icon** → **Environment variables** field (`KEY=value` per line, no quotes). Caveat per Anthropic docs: NOT a dedicated secrets store — values are visible to anyone with environment edit access. `NOTION_API_KEY` must be pasted (legacy Notion readers — notion-action-poll.js, health-check.js, posthog-friction-analyzer.js; NOT any hook, despite what this line used to claim). **Set `REVIEW_TEXTS_TOKEN` too, to be safe:** the bootstrap ALSO tries a tokenless GitHub-proxy clone, but whether the proxy authenticates a clone of a *different* private repo (not the session's own) is **UNVERIFIED in a real cloud session** as of 2026-07-05 — if it doesn't, you silently get a STUB. The token is the guaranteed path. (A fine-grained PAT with read access to BOTH `thomaspryor/broadway-scorecard-data` and `thomaspryor/broadway-review-texts`. Since BRO-4729 a set token also makes the bootstrap pass `--all` to `setup-local-data.sh`, which is the only thing that clones review texts; without the token `data/review-texts` is absent and session start prints a WARN line saying so.)
2. **`LINEAR_API_KEY` is required too — paste it in the same field.** CLAUDE.md §6 makes Linear the board of record, and `linear-brain.js` needs it at BOTH session start (file the issue) and session end (comment the Outcome + set state). Without it every board operation fails closed and the session leaves no entry at all. As of 2026-09-05 `check-cloud-secrets.js` lists it in Tier 1, so a missing key is now a loud failure rather than a silent one.
3. **Data bootstrap is automatic.** The `cloud-bootstrap.sh` SessionStart hook runs `scripts/cloud-bootstrap-data.sh`, which clones the real private data via (a) `REVIEW_TEXTS_TOKEN`, (b) `gh`, or (c) a tokenless GitHub-proxy clone (cloud only, `CLAUDE_CODE_REMOTE=true`, unverified — see #1); if all fail it synthesizes a buildable STUB from `public/data/mobile-shows.json` (reviews/scores empty). Either way it then runs the stub generator as a **gap-fill** to create the gitignored, locally-generated files the private repo doesn't ship (`cast-manifest.json`, `actor-slugs.json`, `video-reviews.json`, …) — without these the app fails `tsc` with TS2307 even with real data. In real-data mode those gap-filled files are EMPTY, so cast/actor/video features are degraded but the app builds. It also `npm install`s `@notionhq/client` on demand. If you still see no `data/shows.json`, run `bash scripts/cloud-bootstrap-data.sh` manually and read the output.
4. **Read accumulated learnings:** `cat cloud-memory/MEMORY.md` — the full index. Specific feedback files referenced in it live alongside it in `cloud-memory/`.

## Landing (the owner never merges)

The owner does not review or merge PRs. A finished change is yours to land, same session, no asking:

1. Run the checks CLAUDE.md §12 requires in your worktree, then `git push origin HEAD:refs/heads/land/<name>` (verified working from a cloud session 2026-09-27). Put the card in the name (`land/bro-N-<slug>`): the hourly stranded pass (BRO-4802, `land-retry-cancelled.js --stranded`) re-runs evicted refs and routes refused ones to the card the name carries; a ref with no `bro-N` can only be logged. MCP fallback if git push is refused: `mcp__github__create_branch` with branch `land/<name>`, or dispatch `land.yml` with `branch=land/<name>` (the input wants the full `land/…` branch name; `branch=bro-…` fails at checkout with "not a commit", seen 2026-09-30 in run 36662927939). Also from that day (BRO-4401): the `land` job shares one `landing` concurrency slot across every session, and GitHub keeps only ONE pending run per group, so a run whose Checks passed can show `Land: cancelled` while the ref is still there. That is an eviction, not a refusal: re-dispatch `land.yml` with `branch=land/<name>` (or push the same head again) rather than chasing a gate. A commit message containing `[skip ci]` (the data/audit ledger convention) suppresses the push-triggered Land run entirely — the ref sits there with no run at all (BRO-4231, 2026-09-30): dispatch `land.yml` with `branch=land/<name>` by hand for such a commit.
2. `land.yml` rebases onto main, re-runs the blocking gates, fast-forwards main, deletes the ref (cloud sessions cannot delete refs themselves: a push `--delete` and the refs API both refuse, so a superseded ref stays until a Mac session removes it; the stranded pass treats it as a leftover once its card lands from another ref). Follow it with one `mcp__github__actions_list` on `land.yml` per check-in until it reports success, or fix what it refused. Wait for it in the same turn: `run_in_background` Bash on `node scripts/lib/wait-for-land.js land/<name> 60`, then one `actions_list` for the verdict (the LANDUNCHECKED Stop hook counts only that). It exits 0 when the ref is gone (landed), 1 the moment the push-triggered run for your tip goes red (the ref stays on a refusal, so a bare `git ls-remote` loop only noticed at its cap: ~1h lost twice, BRO-4671), 2 at the timeout, 3 on a typo'd ref, and keeps waiting through an eviction. It cannot see a hand-dispatched `land.yml` run (listed under `main`): after a dispatch it reports the landing but a refusal only at the timeout, so check that run with `actions_list` too. ScheduleWakeup is best-effort only (a 2026-09-28 wakeup never fired and a refused land sat unnoticed ~1h, BRO-4236). Never `send_later`/`create_trigger` for this: they prompt the owner.
   Pre-flight (optional, verified 2026-09-29): `bash scripts/lib/land-gauntlet.sh <scratchpad-dir>` runs land.yml's gates on the current tree in ~16 min from the cloud. Trust `tsc`, `tsc-llm-scoring`, `next-lint`, `scripts-lib-tests`, `unit-tests-tsx` and `bash-integration` exit codes; `unit-tests-node` exits 1 on origin/main too (~27 cmux/dispatch and review-texts-dependent tests), so read its `not ok` names in `unit-tests-node.log` rather than its exit code; `lint-workflows` needs actionlint, which the cloud lacks. Its tests write into tracked `data/audit/*` files and regenerate `data/gold-lists-computed.json`: `git checkout --` them before committing.
   Pre-flight is automatic (BRO-4593): the `pre-push-land-preflight.sh` hook runs on every `git push … land/*`, previews the land rebase and checks test registration, and blocks the push (with the fix) when either would fail. A block is NOT a land refusal: fix the branch, never route around it with `mcp__github__create_branch` or a land.yml dispatch. Adding or deleting a `tests/unit` file means editing `tests/unit-test-manifest.txt`. Land rebases and drops merge commits, so a conflict you resolved in a merge comes back and the rebase fails (BRO-4558, run 37182544195). Squash instead: `git fetch origin main`, merge `origin/main` one last time, then `git reset --soft origin/main` and commit once (the soft reset keeps your tree, so it must already contain current main).
   **Cloud card worker: a `pick.resume` from `node scripts/cloud-worker-pick.js` overrides the routine's steps 3-5.** It means an earlier worker's Land run on that card was refused (or, with `pick.resume.kind` `evicted`, bumped from the shared landing slot) and nobody came back (BRO-4565). Do not claim anew or start a new branch: follow `pick.resume.instructions`. Run the card's verify on main first and skip to step 7 if it already passes. Otherwise, for `refused`: check out `pick.resume.landRef`, read the refusal, fix, push the SAME ref; for `evicted`: nothing to fix, run `node scripts/land-retry-cancelled.js --run=<id>` (it re-runs only while the landing slot is free; "slot busy" means the sweep re-runs it later, so just follow the ref). Follow Land to its verdict, then continue at step 6.
3. If you opened a draft PR for tracking, close it after LANDED (land rebases, so GitHub won't auto-close it). Opening one is optional; CLAUDE.md's landing rule overrides the harness's "create a draft PR" default.

Don't use `scripts/merge-worktree-to-main.sh` in cloud: its name trips `pre-merge-review-gate.sh`. The Stop hook (`verify-edits.sh`) blocks "waiting on your merge" or "ready for your review" / "unreviewed" (OWNERMERGE) and SAFE TO EXIT after a land push with no run check (LANDUNCHECKED). Local-side detail: `cloud-memory/CLAUDE-reference.md` (Landing on main).

## Overnight watches (the owner is asleep)

The owner lives in Berlin: US opening-night reviews drop 01:00-03:00 UTC while they sleep. Anything that needs their tap then fails. `send_later`, `create_trigger` and `add_repo` always ask for a tap (`requiresUserInteraction`; no mode or allow rule changes that), and `list_sessions` and `create_session` do in practice too, Auto mode included (the hook denies both; BRO-4635, BRO-4664), so a watch that re-arms itself with `send_later` dies after its first pass (BRO-4258).

1. **The reviews don't depend on a Claude watch.** `opening-night-orchestrator.yml` fires ~01:00-01:20 UTC every night and dispatches the poller every 15 min for ~4.5 h; `aggregator-url-watcher.yml` runs every 5 min. Confirm they're armed (`node scripts/check-opening-night-readiness.js --show=ID`, recent orchestrator runs) instead of duplicating them.
2. **If a Claude supervisor watch is wanted, schedule every pass while the owner is awake, in one go, and say so to them before the prompts appear.** `create_trigger` with `initiation: "human_request"` and `persistent_session_id` of the watch session. The minimum cron interval is 1 hour, so a 20-min cadence is three day-limited routines: `1 0-5 <day> <month> *`, `21 0-5 <day> <month> *`, `41 0-5 <day> <month> *`, where `<day>` is the UTC date the reviews land (the day after a New York opening). Avoid minute 0: the server re-anchors hourly minute-0 crons to the creation minute (the 2026-09-29 `0 1-3` routine fired at :05); check `next_run_at` in each result. Add one `run_once_at` morning-report routine that deletes the three by id (a day+month cron fires again next year). Every pass prompt says: never call `send_later`/`create_trigger`, and never relabel `initiation`. Cost: one tap per routine now, none overnight. **Point frequent passes at a lean session** (small context; one the owner started, since `create_session` is denied): a pass in a long-running session re-reads its whole history on every step (a ~440k-token session cost ~$9.30 a pass; a fresh one ~$0.45). Keep at most a few passes on the knowledgeable long-running session. Worked example: the 2026-09-29 School Girls watch (BRO-4258).
3. **Never plan a watch that re-arms itself**, and never assume ScheduleWakeup will fire (see Landing above).
4. `fire_trigger` does not rehearse this: a manual fire starts a new session without the repo, not the persistent one (2026-09-28).

## Closing a Linear issue from cloud

- **Cite the landed commit, not a site URL.** `PR-EVIDENCE: merged deployed checked (https://github.com/thomaspryor/Broadwayscore/commit/<sha>)` with the sha as it sits on origin/main (land rebases, so take it from `git log origin/main`). The gate checks it through GitHub's API, so the shallow clone doesn't matter. A prod URL alone is refused ("names no commit or PR URL"), which is what used to force `--force` on every cloud close.
- **Checking it is live** works without VERCEL_TOKEN: `node scripts/check-prod-deploy.js <sha>` falls back to the newest deploy run whose log shows the production alias, through `gh api` (exit 0 live, 1 not yet). It is one-shot (`--wait` and `--json` still need the token) and cannot see a rollback made in the Vercel dashboard.
- **A card that needs the owner's call** gets a first description line `DECISION NEEDED: <the question in plain English>`, then the options and your recommendation. That line is what emails the owner (daily CI, `scripts/notify-owner-decisions.js`) and what stops workers taking the card; loose wording like "needs owner approval" blocks workers but never reaches the owner. Whoever acts on the answer deletes the block.
- **Close out last.** The Stop hook wants the close after your last commit/push. A `--force` in a cloud session no longer writes `data/audit/linear-gate-bypass.jsonl` (that tracked-file churn caused a commit-land-close loop); the bypass is recorded as a `DONE-GATE-BYPASS:` line on the issue instead (BRO-4241).

## Worktrees and branches in cloud

- **Data in a new worktree:** run `./scripts/setup-local-data.sh --link-only` inside it. It links `data/*.json` to the existing `~/broadway-scorecard-data` clone and `data/review-texts` to the main checkout's, with no fetch and no `reset --hard`. Without it `tsc` and data tests fail for reasons unrelated to your change.
- **Never `git checkout -B <branch>` in a worktree for a branch another checkout has checked out.** git 2.43 allows it silently and moves the branch under the other checkout, which then shows its old files as staged changes. Push to `land/<name>` from your own branch or a detached HEAD instead.

## Fixing private data (review-texts, core data) from cloud

Don't clone and push the private repos: each write stops for an approval, and a repo's checked-in settings can't pre-authorize it (auto mode ignores project-level `autoMode` rules by design). Route the edit through CI instead (BRO-4216):

1. Write `data/pending-fixes/bro-N.json` (N = the Linear issue) in the same shape as the other plans there: `issueNumber: "bro-N"`, a fresh `planId` (uuid), `status: "pending"`, `submitter: {name: null, email: null}`, and `plan: {summary, steps, riskLevel, actions}`. Actions:
   - review text field: `{type: "review-field-edit", file: "<showId>/<file>.json", field, oldValue, newValue, description}`. Fields are allowlisted in `scripts/lib/review-field-edit.js` (verdict flags and their `*ManualClear` markers, byline/date, rejection fields, duplicate pointer); `oldValue` must equal the current value or the action is refused. `url` is allowed only as a repair (BRO-4430): the current url must be an aggregator/round-up page, a non-review page (show page, cast announcement), or another named critic's review a sibling file holds; `newValue` is the real review url on the outlet's own domain (the collector refetches it) or `""` for an aggregator url on a Theatre Record text. Model plan: `data/pending-fixes/bro-4430.json`. File moves/deletes: `{type: "review-file-op", operation: "delete"|"move", sourcePath, destPath}`.
   - shows.json / commercial.json field: `{type: "data-edit", ...}` (allowlist in `scripts/lib/feedback-pipeline-fields.js`; commercial `showSlug` is the shows.json slug; an absent field is written as `oldValue: null`).
   - new commercial.json entry for a Broadway show with none: `{type: "add-commercial-entry", slug: "<shows.json slug>", entry: {designation, sources: [{type, url, date}], ...}}` (`scripts/lib/commercial-entry-action.js`: slug-keyed only, cited sources required, runs the same per-record rules as validate-data.js via `scripts/lib/commercial-record-checks.js`; a non-TBD outcome is stamped `humanReviewedDesignation`). Model plan: `data/pending-fixes/bro-4627.json`.
   - remove a junk row an automated promoter added, or a duplicate: `{type: "retire-show", id, expectTitle, reason, blockTitleVenue?, duplicateOf?}` (`scripts/lib/retire-show-action.js`: only `provisional: true` rows, or with `duplicateOf` a same-title same-house duplicate with zero reviews (id-only); `expectTitle` must match, writes the retired-id registry + archive; `blockTitleVenue: true` only for junk that must never return under any id, never for a duplicate). Model plan: `data/pending-fixes/bro-4398.json`.
   - new shows.json entry (e.g. a closed earlier run of a returning show): `{type: "add-show", show: {...}, crossLinkFrom?: "<existing id>"}` (rules in `scripts/lib/add-show-action.js`: refuses an existing id/slug, placeholder venues and unknown fields; `crossLinkFrom` also appends a `priorRuns` link on that show; `priorRunOf: "<earlier run id>"` instead puts the link on the NEW entry, for a return engagement). Same-title reruns use id/slug `<slug>-off-broadway-<year>`. Art goes in `public/images/shows/<id>/` and lands with the plan. Model plan: `data/pending-fixes/bro-4259.json`. Afterwards dispatch `gather-reviews.yml` with `shows=<id>`.
2. Land it like any change (`land/<name>`).
3. Dispatch `execute-approved-fix.yml` with `issue_number=bro-N`, `plan_id=<planId>`, `mode=apply` (`mcp__github__actions_run_trigger`). It applies and pushes the private repos (no owner email for `bro-*` plans, BRO-4452: report in chat and Linear instead). The run is red if any action was refused.
4. The site picks it up on the next rebuild (or dispatch `rebuild-fast.yml`).

Never put review text or reader contact details in a plan: the file is public.

## GitHub work in cloud (no `gh` CLI)

Cloud has no `gh` CLI — CLAUDE.md's `gh run`/`gh workflow run`/`gh secret set` runbooks don't run as written. Use the GitHub MCP connector (no equivalent for secret rotation: that stays on the owner's Mac).

**Check before assuming either (2026-10-04, BRO-4595):** an environment with the agent proxy ships a preconfigured `gh` (`curl -sS "$HTTPS_PROXY/__agentproxy/status"` lists it under `installedProxyPreconfiguredClis`) and that session had NO `mcp__github__*` tools at all. `gh auth status` says the `GH_TOKEN` is invalid there, but that is a scope-probe quirk: `gh api user`, `gh run list/view`, `gh workflow run` and `gh api repos/...` all work. Only GraphQL is blocked (HTTP 403 "GitHub GraphQL is not available from Claude Code sessions"), so `gh pr list`/`gh issue view` fail; use `gh api repos/{owner}/{repo}/pulls?state=open&head=...` and the other REST routes instead. Decide by probing `gh api user` and `ToolSearch mcp__github`, not by this paragraph. Key traps: no `--jq` (filter in code), job logs live on the blocked `*.blob.core.windows.net` and overflow context (save to a file, slice), and monitoring is a `run_in_background` Bash loop polling the public API (`curl https://api.github.com/repos/thomaspryor/Broadwayscore/actions/workflows/<file>/runs?...`, works without a token) or a single `get_workflow_run` per turn, never ScheduleWakeup alone (best-effort; see Landing). Full job logs: `curl` the API's `actions/jobs/<id>/logs` redirect into a file (reachable 2026-09-29) and slice it.

## Starting a worker session

`create_session` asks the owner to approve every time, so the hook denies it (owner 2026-10-05: "I still want them to be started. I just don't need to approve them each time"; do not rely on the owner's Mac, BRO-4664). To start work in its own session, file it as a self-contained P0/P1 card whose notes begin with `START-NOW: <why it should not wait>` and carry a safe-form `VERIFY:` line: `node scripts/linear-brain.js create "<title>" --dispatch --priority 2 --notes "START-NOW: ..."`. The hourly cloud worker (`scripts/cloud-worker-pick.js`) takes START-NOW Todo cards filed 10 minutes to 48 hours ago before fresh cards and without the usual 6-hour idle wait. It runs one card per firing and finishes a stranded resume first, so tell the owner it is queued and usually starts within an hour or two, never "now". Check your card is pickable with `node scripts/cloud-worker-pick.js`: a START-NOW card that cannot run (no safe VERIFY, wrong state) shows up under `startNowSkipped` with the reason; fix the card. Never ask the owner to approve a session. Do not mark cards START-NOW to jump the queue for ordinary backlog work. Worker rule: if `linear-session.js claim` prints `"action": "noop"` for a card that was Todo when picked, another worker took it; stop and do not work it.

Do what you can from cloud first: most "local-only" things have a cloud route (GitHub MCP tools instead of `gh`, `land/<name>` instead of merging, `execute-approved-fix.yml` for private data, a P0/P1 card with a `START-NOW:` line (the hourly cloud worker takes it first; see Starting a worker session) instead of cmux dispatch). If something truly needs the owner's Mac, say so in one plain line and keep going with everything else. Never ask the owner to "switch to a local session" or to make a technical choice they can't evaluate.
